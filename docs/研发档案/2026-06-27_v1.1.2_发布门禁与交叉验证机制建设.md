# 发布门禁与交叉验证机制建设

## 研发日期

2026-06-27

## 版本号

v1.1.2

## 需求背景

随着 MMN 汽车营销引擎功能持续增加，单次功能修改可能影响页面渲染、数据口径、按钮交互、研发档案归档和版本交付稳定性。为降低迭代风险，需要建立标准化交付门禁机制，在每次功能迭代、问题修复和流程优化完成后进行交叉验证。

## 问题分析

此前功能交付主要依赖单项检查，容易遗漏以下风险：

1. 前端元素移除后，旧事件绑定残留导致页面渲染中断。
2. 页面按钮文案已调整，但实际页面未加载最新资源。
3. 业务口径修改后，首页核心字段未被浏览器真实验证。
4. 功能修复完成后，研发档案可能未同步归档。
5. 单纯语法检查无法覆盖真实页面运行状态。

## 技术方案

本次新增 MMN 发布门禁机制，形成多层交叉验证：

1. 代码语法层：检查前端脚本与后端脚本语法。
2. 页面运行层：通过本机浏览器访问本地服务，捕捉页面运行错误。
3. 核心交互层：检查决策驾驶舱关键字段、导入按钮、页面切换和策略入口。
4. 产品口径层：检查驾驶舱是否仍暴露不必要的文件格式文案。
5. 研发档案层：检查功能变更是否同步更新研发档案，并拦截不符合归档规范的描述。
6. 服务可用层：本地服务未启动时自动启动临时服务进行检查。

## 功能实现

1. 新增 `scripts/release_gate.sh`，作为统一发布门禁入口。
2. 新增 `scripts/release_gate.js`，执行真实浏览器页面验证。
3. 发布门禁覆盖驾驶舱项目、品牌、车型、样本规模和导入按钮检查。
4. 发布门禁覆盖研发档案规范检查。
5. 本地服务未启动时，发布门禁可自动启动临时服务。
6. 发布门禁失败时退出并阻止交付。

## 版本变更说明

本次版本记为 v1.1.2，属于研发流程和交付质量保障机制升级。该版本不改变业务功能，不改变数据结构，主要用于建立后续迭代交付门禁。

## 后续计划

1. 每次功能更新、问题修复和流程优化完成后，必须运行发布门禁。
2. 根据新模块增加新的页面级检查项。
3. 将数据导入、RAG策略、高管蒸馏、达人库和垂媒竞争格局逐步纳入专项检查。
4. 持续补充研发档案，使版本演进长期可追溯。
